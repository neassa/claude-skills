## 0. Three premise corrections

1. **There is no `frontend/upload` registry key or mount on lit-2610.** `grep frontend/upload` over `literatum/conf`, `product/*/conf`, `bridge/conf`, `publish/src`, `bridge/src`, `literatum/src`, the deployconf XSL and platform-tools finds nothing. The only upload landing directory is `backstage/incomingDir` (note 17 §2.1), on IBM `${macro/acs-home-path}/webdav_directories/${macro/product-name}/${server/mode}_upload` (`product/midtier/conf/midtier.props.IBM.xml:124`). Nothing in the cloned `ansible-*` repos references `webdav_directories`; only ad-hoc platform-tools scripts do (`PT/wspc_missing_logs.sh`, `PT/releaseTracker.py`). **Model gap:** the SFTP/WebDAV server that publishers drop zips into, and the NFS mount of `webdav_directories` onto the backstage host, live in a repo that is not cloned.
2. **Gaia is not part of ingestion.** `grep -ril gaia B/` returns nothing. Ingestion validates with a local DTD parse plus Schematron and stores XML/PDF on disk; HTML/Gaia transformation is request-time on web nodes (note 12 §1.4). "XSLT steps" in ingestion are the IssuePrimeBuilder prime build and the TOC/Schematron transforms, not Gaia.
3. **There is no REST content-deposit handler in the literatum REST tree.** `grep 'api/rest/handlers/.*(deposit|submission|upload)'` in `literatum.props.xml` finds nothing. Programmatic zip submission is the bridge/Passport CMS service layer (`CmsPublishUtils.processUploadedSubmission`, §1.5), not `/rest/`.

### 2.3 Where errors go, and when the submission's ERRORLEVEL is set
- `backstageLog(code, …)` (`literatum/src/java/com/atypon/literatum/util/error/ItlLog.java:39-157`) does two things: logs through the `Backstage` logger (level from the error code) **and** creates `BkstgErrorLog` rows for every content item in the current `ItlActionContext`. With no content in context it logs ERROR `No assotiated content could be inferred from current Context; ErrorCode will not be saved in the database` [sic] and the code is lost from the DB. Stack traces are saved when the flag at `:65` is on (`backstage/…stack…`, masked).
- The rows are held in memory as a log group and flushed in `ProcessArticlesProc.commit()` (`B/ProcessArticlesProc.java:364-397`, inside the transit's commit transaction): `BkstgErrorLog.saveAndClearLogGroup(backstageId, now)` → `LOG_BACKSTAGE_ERROR`; `SeverityLevel.mergeLevels` → `BackstageSubmission.update(... groupErrorLevel, processedDois, warningCount, errorCount, externalId)` → `BACKSTAGE_SUBMISSION_INFO.ERRORLEVEL/ERRORCOUNT`; then `updateBackstageStatistics`, `generateEventsForAnalytics`, `generateEventsForSitemaps`.
- **Consequence:** if the JVM dies between `fire()` and `commit()`, the error rows for that attempt are lost and the event is re-run from scratch when its lock is released (note 17 §2.3).

### 2.4 Make-live decision (`ProcessArticlesProc.createMakeLiveCase`, `:399-482`)
- Runs after processing. The issue must exist in STAGING (`CREATE_MAKE_LIVE_ISSUE_MISSING` 395). If a make-live is already scheduled for the DOIs, it returns with a warning. Nothing processed and no attachments → no move.

  - `makeLiveDate != null` → `BACKSTAGE_STATUS=SCHEDULED(2)`, `SimpleGenericWorkflowCase(StartScheduledBackstage)` with token attribute `submissionId`, `kase.schedule(makeLiveDate, null, true, priority, ENGINE_BACKSTAGE)` → a `wf_schedule` row (priority HIGH when `BOOST_SCHEDULED_MOVES`), plus `WF_VARIABLE 'submissionId'` when XML token serialization is on.
  - else `MoveArticlesWorkflowCase.create(issue, moveSubmission, priority, engine)` right away.
- Logs `CREATED_MAKE_LIVE` (394) `<issueDoi> at <date>|now <dois>` or `CREATE_MAKE_LIVE_FAILED` (380). Priority/engine come from `ProcQueueInfo` (`CREATE_MAKE_LIVE_DEFAULT_PRIOENG` 397 when none).
- `StartScheduledBackstage.execute` (`B/workflow/StartScheduledBackstage.java:24-36`) reads `submissionId` (and a deposit feed id) from the token, runs `StartScheduledBackstageProc`, and deletes the SCHEDULED status on commit. `find(submission)` (`:38-58`) is the SQL the UI uses to show a pending schedule (`wf_schedule` joined to `wf_variable` or `wf_schedule_token_map`/`wf_token_value`).

**"Publish" therefore means:** the `PUBLICATION`/content rows get the new `area` bit and folder, the source rows and files are removed, cited-by and system links flip on, `.info`/TOC files are rewritten, staging index documents are deleted and production documents submitted through Kafka, deposits and CDN uploads are queued. ### 3.4 Content versions, embargo and release dates
- Future issue types are **areas**: `ContentArea.FUTURE_AREA_BITS` (AOP, JA, FORTHCOMING), plus STAGING, PRODUCTION, EMBARGOED, CIL, PROOFING. `identifySubmissionMode` maps the target to `TO_PRODUCTION|TO_STAGING|TO_AOP|TO_JA|TO_FORTHCOMING|TO_PROOFING` (`B/MoveArticlesProc.java:132-150`). `ArticleVersions.keepContentVersions` decides whether moving to production replaces the future version or keeps it (`Article.java:1296-1304`); `ArticleVersion` sub-folders hold previous versions.

## 5. Failure handling: retries, suspension, kill, cleanup

- **Event lifecycle texts** (`W/engine/EventProcessor.java:128-281`, logger `Workflow` → `log/workflow.log`, `log4j2.xml:126-127`, `:605-608`): INFO `start processing event <id>, <type>, fire <F>, case <C>` → `processing of event … finished`; failures: ERROR `processing of event … failed on SQLException error code: <n>` (INFO when the DB driver says it is a network error), INFO `processing of event … requested reschedule at <ts>[: <msg>]` for `RescheduleWorkflowException`, ERROR `processing of event … failed` + stack for everything else; `processing of event … was interrupted` on shutdown (lock released: `UPDATE wf_event SET lockedBy = NULL, lockTime = NULL`; FATAL `cannot release a lock on event` if that fails).
- **Suspension** (`:230-266`): `UPDATE wf_event SET lockTime = <until>, suspendCount = <n+1>, lockedBy = -2`. `until` = the reschedule's `runAt`/`delay`, else `ZombieKiller.computeSuspendTimestamp(suspendCount, isDbDeadlock)` (`W/engine/ZombieKiller.java:155-172`): deadlock → 10 s (INFO `processing failed due to a database deadlock`); count 0 → 10 min; 1 → 1 h; 2 → 6 h; ≥3 → **1 day**. If the suspend UPDATE itself fails: FATAL `cannot suspend event <id>` and the id is parked in `ZombieKiller.addUnreleasedEvents`. `AlarmRobot.alarmCreatedAll()` is poked when the release is < 5 min away.
- **Prim fire execution** (`:540-631`): `transitDef.createFire(fire)` → `transit.fire()` → in one `Transaction.executeInterruptible`: `WfDbEvent.delete(eventId)` is the claim (`event was processed by someone else` when 0 rows) then `transit.commit()`. `FireKilledException` → INFO `fire <id> has been finished/killed already`. On any failure the fire's `startTime` is reset to NULL (`:616-629`, `unexpected error while cleaning fire startTime:`). Thread name becomes `<pool>-caseid-<C>-fireid-<F>` while running (`:572`), useful in thread dumps.
- **There is no dead-letter queue.** A failing event retries forever at most daily. Terminal outcomes are only: the transit succeeds; the case is **killed** (`WfDbFire.kill(killerId)`, `W/engine/data/WfDbFire.java:216-245`: deletes the case's `wf_event` rows, `state=2`, kills sub-fires, deletes `WF_ALARM` rows, calls the case listener → `BACKSTAGE_SUBMISSION_INFO.killed=1, SubmissionKillerId`; from WAT or `backstage.sh processing.cancel` = `CancelSubmissions`); or `SchedulerRobot.cleanupCasesForDeadClass(className)` (`:267-342`) deletes schedule entries and kills live cases whose `gw_className` no longer exists (prints `Found N schedule entries associated with our dead class.` … `Db is clear of active tasks relating to <cls>: true`).
- **`CleanupRobot`** (`W/engine/CleanupRobot.java`, read fully): `WfCleanupRobot`, cluster mutex `workflow/cleanup…` (`:47`, masked), deletes finished top-level cases (`state <> 0`, `endTime` older than `workflow/cleanup…max-age-days`, batch size and per-case delay also under `workflow/cleanup…`, `:30-38`; invalid values → `IllegalArgumentException` at robot construction, i.e. at backstage startup). Logs `loading finished cases older than N days`, `loaded N cases`, `case <id> could not be deleted`, `exception occurred`; sleeps 1 h when idle, 5 min after an error.
- **Locks that can stick:** content locks (`AbstractPublicationContent.tryAcquireLock` → `LockedContentException`), cluster mutexes `IssueCreate` (30 min timeout), `IssueInstantiate`, book parent (`Cannot acquire lock`), depository connection (`SubmitProc` → TEMP_FAILED → 4-hour alarm), `workflow.checkNewDef.<file>` (note 17 §1.3). Under `PassportClusterMutex` the underlying errors are in `log/akka/passport-cluster.log` (note 17 §2.4).
- **Restart in the middle of a move:** the transit re-fires; `MoveFatalErrorHandler` recognises an already-moved issue (§3.2); otherwise the source may already be gone → `CONTENT_ALREADY_MOVED` (367) or `SUBMISSION_ALREADY_IN_AREA` (213), and a later staging→production move of the same issue can hit the embargo conflict text (§3.1).
- **Operator views:** WAT Backstage → Processing Queue (running cases; note 17 §2.7), submission report (`SubmissionReportContextMenu`, severity tree from `LOG_BACKSTAGE_ERROR`), content tree context menu (Move/Reprocess/Delete/Invalidate HTML), `/action/wfengine?action=…` case/fire graphs and `/action/adminBackstageWorkflow` (`services.props.xml:1230-1234`). DB: `BACKSTAGE_SUBMISSION_INFO` (`ERRORLEVEL`, `ERRORCOUNT`, `ENDTIME`, `KILLED`, `SubmissionKillerId`, `EXTERNALID`), `BACKSTAGE_STATUS` (status ids `publish/src/java/com/atypon/publish/acs/backstage/Status.java:14-33`: 1 PROCESSING, 2 SCHEDULED, 3 PREPROCESSING, 4 DEPOSIT, 5 LINKING, 6 CALC_DEPOSITS, 7 CALC_LINKING, 8-11 WAITING_LINKING_CROSSREF/ISI/PUBMED/JSTOR, 12 WAITING_TEMIS, 13-15 WAITING_DEPOSIT_CROSSREF/ISI/PUBMED, 16 INDEXING, 17 CDN, 500 COPYING_DBPUB_ENTITIES), `LOG_BACKSTAGE_ERROR`, `WF_EVENT`/`WF_FIRE`/`WF_SCHEDULE`/`WF_ALARM`/`WF_VARIABLE`, `INDEXING_STAT`, `GENERIC_DEPOSITORY` + deposit batch tables.
