# 27. Filter re-check of negative claims in notes 09–16 (2026-09-25)

**Why:** earlier readers filtered greps with a case-insensitive ` -P ?[^ -]` pattern. That silently dropped every line containing ` -p <product>` (for example `ansible-actions -s gaia -p mms`, `patch.py -p …`). So any "no callers / unused / dead / not referenced / CLI-only" claim built on such a grep could be wrong.

**How:** I found candidate claims by searching notes 09–16 for `no caller|not called|never called|unused|dead code|dead|nothing (calls|invokes|uses)|no .* calls|not referenced|only .* calls|not used|CLI-only|none of`, plus a second, broader pass. Then I re-ran each underlying search with `tools/safe_view.py --grep`, which is case-insensitive and does **not** drop `-p` lines. Repos searched: deployserver (config + src), platform-tools, ansible-inventory, ansible-tools, the relevant ansible-* repo, opstool, deployconf, and opscommon where it applied. Everything was read-only.

**Repo state used:** deployserver master `b726c83`, platform-tools master `b00c49f`, ansible-inventory master `0e3ac30`, ansible-searchservice master `00d600e`, ansible-ingestion main `24b39c6`, opstool master `4562351`, deployconf main `ad1c87a`, ansible-tools master `750b441`, opscommon master `7d5d1ac`.

**Tally:** 14 claims checked. 11 STILL TRUE, 2 WRONG (both the same ConfHelper gap, in notes 11 and 15; note 18 had already closed it; the `-p` filter did not cause it), 1 UNCLEAR. **None of the WRONG results came from the `-p` filter.** Every filter-sensitive caller claim still holds.
