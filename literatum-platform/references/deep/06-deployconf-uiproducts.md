## 1. How deployconf flows (pipeline)

1. **Edit**: someone pushes to a side branch. `pr-creation.yml:3-17` auto-opens a PR to `main`.
2. **Label `automerge`**: `pr-merge.yml:8-68` runs `xmllint --noout` on changed `deployconf.(literatum|staging|midtierbeta|atypon|lts|migration|readonly|gcp|performance|rorehearsal|office-jordan-cip|gcp-rehearsal|cip).xml` (`:29-35`). This is a **well-formedness check only, not XSD** (`:53`). The job then merges through the REST API (`:79-93`) and sends a `repository_dispatch` `push-hook` (`:94-97`).
3. **Post-push** `push-hook.yml`: for each changed allowed env file it curls deployserver `/run?action=DeployConfValidation` and then `/run?action=ConsulPopulate&args=dc|False|True|<acct>` (`:42-61`). CIP accounts go to `cip-deployserver`.
   - `DeployConfValidation` → `~/scripts/deployConfValidation.sh -a <acct> -r <rev>` (`deployserver/config/actions.xml:2146-2151`). This runs `git reset --hard origin/main; git clean -fdx; git pull` in `~/.litconfig` (`deployConfValidation.sh:47-48`), then **XSD** validation (`:50`). On failure it opens a LIT P1 Jira ticket, sends email and posts to chat (`:57-59`). It **always** prints `Validation has been completed` (`:61`), which is the action's validate-txt. So the deployserver action succeeds even when the XSD check fails, and `-r` (revision) is ignored.
   - `ConsulPopulate` → Rundeck job via opstool (`actions.xml:1157-1163`). This loads deployconf into Consul `deployconf/<env>/products/<p>/<fam>/...`, which is read by `functions.sh:526` and `deployPropsDeployconf.py:224-234`.
4. **Direct path**: `deployconf-auto-update.yml` (`workflow_dispatch`, staging|midtierbeta only). It applies JSON `[{path,value}]` with `xmlstarlet ed -u` and **pushes straight to `main`** (`:63-92`). This skips the PR and xmllint gate. The push still fires push-hook, because the files are in its `paths`.
5. **Per-host consumption**: `~/.litconfig` is the deployconf clone, and `~/deployconf.xml` symlinks to `deployconf.<acct>.xml`.
   - `setprod` (`functions.sh`) exports SG_BRANCH, PUGRENDERER_*, SOLR/KAFKA/REDIS/CASSANDRA/ZOOKEEPER_* via xmllint (`functions.sh:303-323`).
   - `rebuild.py`/`DeployConf` (`platform-tools/deployconf.py`) drives build and deploy.
   - `deployPropsDeployconf.py:83-110` runs `xslconfig/deployconf.<acct>.xsl` (or falls back to `deployconf.xsl`) with ~30 params. The output is `$DEPLOY_HOME/webapps/<prod>/WEB-INF/deployconf.props.xml`, which Literatum loads at startup (`LiteratumRegistryFactory.java:154-155`).
6. **Ansible**: `ansible-inventory/inventory.py` reads `~/.litconfig/deployconf.<acct>.xml` (`:133-139`) after `os.path.expandvars` (`:149-153`). It emits dynamic inventory per service: solr, consumer, cassandra, pugrenderer, gaia, redis, zookeeper, kafka, and others (`:43-129`). The ansible-{solr,consumer,cassandra,gaia,redis} roles consume it.

### 3.1 Anomalies found (verify before acting)
1. **prod chrysalis → undefined pugrenderer cluster.** `literatum.xml:10689` product chrysalis (enabled, pre-prod) sets `<pugrenderer-cluster>prod-pr-chrysalis</pugrenderer-cluster>`. The only cluster defined is `literatum-pr-chrysalis` (`literatum.xml:671`). Effects:
   - XSL emits `frontend/nodejs` with an **empty `address` set**. It has no `otherwise` branch (xsl 566-632).
   - INV `pugrenderer.py` `setCommon` finds no cluster, so chrysalis gets no product group, and `literatum-pr-chrysalis` gets no `develop` styleguide version.
2. **prod `cassandra-pim-literatum3` lists a literatum4 node.** `literatum.xml:718` has `prod-cassandra-literatum4-pim-live-2`, which is also in `cassandra-pim-literatum4` (`:688`). `prod-cassandra-literatum3-pim-live-2` is still declared as a machine (`:1550`). This looks like a copy/paste error, or a deliberate host swap.
3. **prod was family `w`** (`literatum.xml:8936`, atm model family also `w`) vs `W` in beta/stag. Name-plus-family lookups (XSL, INV ids `was-w`, DS) are case-sensitive.
4. **Disabled beta products still feed gaia and pugrenderer.** `gaia.py` does not filter `enabled`, so for example disabled beta `app` (2.2.75) and `lup` still get gaia scopes. `getStyleguideVersions` also counts disabled products' SG versions.
5. **`lit_worktrees_cleanup.sh`** keeps only worktrees referenced by `product[@enabled="true"]/source` (`:25,50`) and SG branches of enabled products (`:70-72`). Worktrees used only by disabled products (51 in beta) or only by `previous_source_branch` (the gaia rollback key) get deleted.

## B2. What Build-Deploy-Styleguide.sh runs, end to end

**Trigger: deployserver `ProductBuild` → `MacroExplodeBuild.addStyleGuideBuildActions`** (`CreateActionMacro.java:955-975`)
- It adds `ProductBuildStyleguide` only when:
  - `<styleguide><version>` is non-empty, and
  - it is not the case that `pugrenderer-cluster` is absent while k8spugrenderer is configured (`:958-963`).
- `ActionModelVisitor.initStyleguideModel` (`:143-168`) sets:
  - `branch` = `<version>`
  - `productGroup` = `<group>`
  - `nodeVersion` = the pugrenderer cluster's `node_version`
- The command template is `cd ~/scripts; Build-Deploy-Styleguide.sh -p <prod> -f <family> -b $branch -a <account> [-g $productGroup]` (`actions.xml:2014-2024`).
  - The only success check is the text `BUILD COMPLETED`.
  - **`nodeVersion` is computed but never passed.**

**Script steps**
1. Sources `~/.bashrc`, `aliases.sh`, `functions.sh` and `jenkins/styleguide/operations.sh` (BDS:3-6). Defaults: node 14.16.0, npm 6.14.11, `utyponCliStableVersion=1.31.11` (BDS:17-32).
2. `main` (BDS:891-950):
   - Sets the ERR trap (stats "failure"), then parses args (BDS:530-562).
   - On DC, `checkDataCenterLinks` (BDS:808-818) rsyncs `~/.nvm` to `/local$HOME/.nvm`, runs `rm -rf ~/.nvm` and symlinks it.
   - For developer mode, rorehearsal, or when nvm is missing, it runs `initializeEnvironment`: curl nvm 0.35.0, then `nvm install 14.16.0` (BDS:35-46).
3. **Git** (`gitCheckout` BDS:268-304 → `checkoutGitRepoBranchStyle ui-products <branch>` BDS:48-135), in `~/sourcegit/ui-products-branches/<branch>/ui-products`:
   - Existing dir: `git fetch; checkout <b>; reset --hard origin/<b>; clean -fdx; pull origin <b>` (BDS:99-118). **None of these are exit-checked.**
   - New dir: `git clone git@github.com:atypon/ui-products.git --branch=<b>` (BDS:121-127), also unchecked.
   - Then `git status`, `git submodule init` and `git submodule update --remote`, which are checked (BDS:293-302).
4. **Node/npm** (BDS:343-395):
   - Sources `nvm.sh`, runs `npm config set prefix …/v14.16.0` and `npm i -g npm@6.14.11` (this runs *before* `nvm use`), then `nvm use --delete-prefix 14.16.0`.
   - `loginToAtyponRegistry` (BDS:848-873) sets `@atypon:registry=https://npm.pkg.github.com` with static credentials: `<secret-bearing line at Build-Deploy-Styleguide.sh:864-872>`. These credentials are echoed into the action log.
   - `npm i -g @atypon/utypon-cli@latest -f` when the user is midtierbeta or staging, otherwise `@1.31.11`. **Unchecked.**
   - Sets `NODE_ENV=production` and `NODE_OPTIONS=--max-old-space-size=25000`.
5. **Build** (BDS:448-490):
   - With `-g`: `cd <group>` (**unchecked**), `rm -rf node_modules`, `utypon build optimized --productsPath=$PWD --noSudo --noContainer --threadsCount=10 --ramCount=10`, then `checkBuildSuccess`, then `cd <product>` (unchecked).

   - **utypon's exit code is ignored.** `checkBuildSuccess` (BDS:306-327) tars `build.log` to `~/logs/<acct>/<prod>/UI/build.tgz` and greps for `All Products Have been Built Successfully`. If it is absent, the script prints `Failed to Build The Product` and exits 1.
6. **releasedAssets** (BDS:160-266):

   - Copies it to `~/webdav_directories/<prod>/<fam>/` and `./releasedAssets/`.
   - On DC, calls `Zip-uploadToAWS`.
7. **Package** (`Zip-uploadToAWS`, BDS:564-650):
   - Tars the product dir, or the **whole group dir**, including node_modules.
   - Output: `~/sourcegit/styleguide_new_<acct>_<prod>_<fam>.tar`, then `gzip -f`, then `mv` to `~/warfiles/`.
   - The S3, FTP and webdav upload code is commented out (BDS:622-647).
   - Prints **`BUILD COMPLETED`** (BDS:649), which is deployserver's success marker.
8. **Deploy / pickup**
