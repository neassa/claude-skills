# False successes: Success rows you can't trust

Pass/fail is text matching, so a green step can hide a failure. Each row says why, and where it was verified.

| Step | Why Success can be wrong |
|---|---|
| ProductBuild | build-time source patch failure is swallowed (builds unpatched); WAR may be missing after `BUILD SUCCESSFUL` |
| ProductBuildStyleguide | `BUILD COMPLETED` printed unconditionally; git checkout unchecked (stale branch builds) |
| HostDeployStyleguide | runs on **web hosts only** (never bks). Since platform-tools commit `LIT-585088` (2026-02-25) `deployStyleguide.py` only prints `Not Production, Exiting.` + `>>> Finished styleguide deployment` — confirmed live on rmit-beta-web2 (beta, 2026-09-24) and literatum7-prod-web5 (prod utb, 2026-09-23). It deploys nothing, so it can't fail; the styleguide actually built by ProductBuildStyleguide ends up as `~/sourcegit/styleguide_new_<acct>_<P>_<F>.tar.gz` on the tools host. **The styleguide is actually delivered by PugrendererProductDeploy** (runs before the host steps): `ansible-actions -s pugrenderer -p P -f F -a deploy` → `atypon/ansible-pugrenderer` (prod-pr-literatum7 used `4.1`) → copies the released assets from `~/warfiles`, extracts/validates them, creates `styleguide-templates/<SG branch>`, rsyncs the product, invalidates styleguide caches, redeploys the pugrenderer docker nodes (which run on the web machines). Confirmed from prod utb log `c66138c1…` (2026-09-23). So for a styleguide problem, read ProductBuildStyleguide + PugrendererProductDeploy (+ PugrendererInvalidateCache/CfInvalidateCache), not HostDeployStyleguide. |
| HostStop (web & backstage) | success strings are always printed |
| HostStart | can match the pre-start `rstrt -s` if the old JVM survived; only proves a java pid exists |
| HostDeploy | `jar -xf` exit lost; deploys the lexicographically latest WAR in `~/warfiles` |
| ProductPatch | multi-family: first `BUILD SUCCESSFUL` wins; patch runs against the **deployed** webapp, not the new build |
| ansible steps | Pushgateway always reports OK; stale-playbook WARN path |
| CfInvalidateCache | **stub**: `platform-tools/InvalidateCloudflareCache.py` prints `>>> Finished Invalidating Cloudflare Cache` and `sys.exit(0)` at line 26; the real purge code below never runs (run by `deployserver/config/actions.xml:412`; verified 2026-09-25). Stale pages after a deploy → Cloudflare was never purged. |
| PugrendererInvalidateCache | ansible-pugrenderer 4.0/4.1 `roles/released-assets/tasks/released-assets-invalidatecache.yml:3` calls `/invalidateCaches?r=<sg ver>&p=<product>'` with a **stray `'`**. The renderer (UI-Renderer-V2.6.7 `cache.service.ts` `clearAll`) deletes only keys containing both `product` and `release`, so the `'` means it very likely deletes nothing, yet it returns 200 → `COMPLETED SUCCESS`. The flush that works is the parameterless `/invalidateCaches` (`flushAll`) in PugrendererProductDeploy's `create-paths` role (verified 2026-09-25). |
| HostWaitForWebServer | opstool `DeployFamilyAction -t serverup` fetches `/heartbeat?bg=1` with an empty expected text: **any HTTP 200 passes**, even body `1` (DB down / still locked); 404, refused or >3 s timeout fails (`RESULT:FAILURE`, retried to timeout). If the host's own `~/deployconf.xml` matches nothing, it prints `RESULT:SUCCESS` having checked nothing: the tell is no `DeployFamilyAction.<Action> for …` line (notes/18). |
| HostUnlock / HostLock | `DeployFamilyAction.java:70` inverts `-p` (`hasOption('p') ? null : …`), so the product is always null and **the action applies to every product of that family on the host**; unlock stops at the first product that fails (verified; file unchanged since 2019). HostLock has no validator → always Success. |
| HostWarmupTest | verdict = the **first** `***Test Is Succeeded***` / `***Test Is Failed***` line; no marker = Failure (`SshExecuteVisitor.java:830-840`, verified). Retried, then Cancelled, **never blocks the release**. In a 111-run sample (10–25 Sep) none pointed to a bad deploy: 37% harness/test-config (marlin, aami logins; ux3/support/lean not in suite), 41% stale test data (same 404/403/400 pages every run), 22% one page 503 every run. 13 products (marlin, pericles, mms, physio, smp, hope, aha, utoronto, aami, ux3, cabi, app, aps) have almost no passing warm-ups, so compare with that product's history before blaming the deploy (notes/19). HostTestJane (marlin) has never passed on beta/stag. **Why (verified):** each page first logs in via `GET /action/QATestActions?test=impersonate&email=…` (testypon `HTTPAuthClient.java:129-160`). **marlin:** that redirects to Elsevier ID, and qa-automation-xml `recorder-tests/.../hosts/hosts:17-18` (`loadrc-id.elsevier.com`, `id.elsevier.com`) is rewritten by `HostsFilesUtil.addIps` (`:20-29`, docker only) to point at the web host, so the connection is refused on every page. This is a test setup bug (LIT-639552, 2025-08-05), not an outage. **aami:** 403, because the caller's IP isn't in aami's `AUTO_TEST_USER` group (`QATestActions.checkSessionAccess`), which is test data. **Jane 403:** marlin's WS IP allow-list has `127.*`/`10.*` commented out (`marlin.props.xml:603-605`), and opstool `ant bundle` never ships `wsconf/` (reader-verified, notes/23). |
| GaiaDeploy | can go green with nothing changed: new `image_tag` ignored unless `force_recreate=true` (`app-deploy.yml:150-151`); bundle checked in GAR but the container downloads from Nexus; the check regex cuts `2.2.85.1` to `2.2.85`; bundles install asynchronously (updater loop, every 10 s, forever if missing in Nexus); `/actuator/health` is UP with zero bundles. Real state: compare gaia-fe `GET /config` vs `GET /bundle` (notes/22, reader-verified). |
| ansible "no hosts matched" | an empty host group prints `skipping: no hosts matched` and still ends `COMPLETED SUCCESS` with nothing deployed (notes/11) |

Real readiness evidence = HostWaitForWebServer + HostWarmupTest/HostEssentialTest, and the site itself.
| ProductConsumerDeploy | validates `/metrics/ping` (ansible-consumer `roles/validate/tasks/validate.yml:4`, master; verified), the metrics servlet, which doesn't check Solr or Redis (`/ping` does). A consumer that can't reach Solr passes. At runtime the consumer can drop documents quietly: `Failed to process document on core X`, or `Document purged from Redis … exceeded max number of retries` (notes/29). |
| Rundeck-backed actions (ConsulPopulate, GaiaDeploy via Rundeck, UpdateStatusPage) | opstool `RundeckApiService` never reads the job's final status, so the verdict comes from text the job prints. Rundeck GaiaDeploy passes with no pod Running; MountFS is an unconditional echo. The four Audit* actions always fail (their jobs never print `COMPLETED SUCCESS`) (notes/30, reader-verified). |
| HostLock (as a traffic drain) | **HostLock does not take a web node out of the load balancer.** HAProxy's check is `GET /heartbeat?id=achs` expecting `AtyponLiteratumWorksGreat` (puppet-control `site-modules/profile/files/haproxy/literatum-backends.cfg.ctmpl:155-156`, `production` @ e5b11ac; `check inter 3s fall 3 rise 2`). Literatum answers that path from `HeartBeatServlet.checkAchs` (lit-2610 @ c9e4556e, :216-227), which returns the string whenever `checkDatabase()` is OK: the lock test is **commented out** (`/*|| !isUnlocked()*/`, "need to check why LB is sending ?id=achs"). Only the `?bg=1` path (opstool serverup) honours lock/release. So a locked node keeps receiving traffic through Pause1Min, and HostStop kills a node HAProxy still routes to; HAProxy drops it after ≤3 failed checks (~9 s) → a short 5xx burst per web node per deploy (inferred from the two facts; not observed). Verified in code 2026-09-27; live LB behaviour not observed. |
