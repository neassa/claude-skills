## Visitor IP & geo resolution (verified 2026-08-31 against `packages/core/src/plugins/request-meta.ts`)

- `extractRequestMeta()` resolves the client IP as: **with a `cf` object** (Workers runtime only) `CF-Connecting-IP` → first `X-Forwarded-For` entry; **without one** (the node env — CF proxies to the ALB, no Worker, so no `cf` object even though CF headers arrive) ONLY the operator-declared `EMDASH_TRUSTED_PROXY_HEADERS` / `config.trustedProxyHeaders` list. **No socket-address fallback** — on node, an empty/wrong trusted-header list means `ip = null` for ALL traffic. Geo (`country`) comes from `request.cf` only, so on node it's always null — any geo feature there needs an IP→country provider lookup.
- **Regional availability (REQ-043a/b/c) is IMPLEMENTED on `poc` (found merged 2026-09-06)** — site-level, NOT the core request-meta path: `custom/sites/focus/src/utils/regional-availability.ts` + spec `custom/docs/specs/regional-availability/tech.md`. `resolveVisitorLocation()` reads the **`CF-IPCountry` header** (Cloudflare edge geo = "the provider"; no IP-database lookup, and the raw IP is never logged/persisted). Three `undetermined` reasons, all fail-closed to the same 403 when the item carries a block: `missing-ip` (no CF-Connecting-IP/XFF/X-Real-IP at all), `provider-unavailable` (client-IP headers present but no `CF-IPCountry` — edge doesn't attach geo), `provider-unknown` (`XX`/`T1`, or any value outside `VALID_COUNTRY_CODES` — malformed codes like `DEU` deliberately fail closed, not open). Crawler UAs bypass the block but restricted responses are always `private/no-store` (no cache poisoning); preview bypasses entirely.
- **Testing levers:** direct-to-origin (jump host) you can set/omit these headers freely — every scenario is reproducible without VPNs. Through the public hostnames CF controls the headers (verify whether the Atypon-managed literatum.com zone actually attaches `CF-IPCountry`; if not, ALL visitors are `provider-unavailable` and every blocked item 403s for everyone). Debug surface: `GatingDebug.astro` panel shows the resolver result — enabled by **runtime env `FOCUS_GATING_DEBUG=1`** on the deployment (POC only; do not gate on `import.meta.env.DEV`, compile-time false in deployed builds). Denials (only denials) log non-PII via `logRegionalDenial`: `[regional-availability] access denied` + contentId/outcome/reason/resolutionReason/action → CW app log group. ## Terraform gotchas (this stack — each one observed live)

- **Removing a block ≠ disabling it (revert ≠ undo).** Deleting an optional block like `stickiness {}` from `aws_lb_target_group` UN-MANAGES the attribute — live infra keeps its last value and the plan shows NO change (observed live 2026-08-23: reverting the stickiness PR left the ALB sticky). To turn something off, keep the block managed and set `enabled = false`. Rule: after reverting an APPLIED change, a clean plan is a red flag, not a success — verify the off-value appears as a diff. Provider defaults only apply on resource CREATE, not to existing resources.
- **Always `export AWS_PROFILE` first** — bare `aws`/`terraform` runs as `terraform-local` in the WRONG account (045369966266). Simulate/plan results from the wrong identity look plausible. **`AWS_PROFILE=x && terraform init` does NOT export** (shell var only) → terraform falls back to default creds → `S3: HeadObject ... 403 Forbidden` on the tfstate (Laith hit it twice, 2026-10-01). Use `export AWS_PROFILE=x && ...` or the prefix form `AWS_PROFILE=x terraform init`. Profile **`909176971711_AWSNonProdASTechAdmin`** (static creds in `~/.aws/credentials`, not `~/.aws/config`) ran 30-node-app init/plan/apply fine, including the ACM data source (no `acm:GetCertificate` failure).
- **Profile split (verified 2026-08-24): terraform needs SRE, DB-migrator needs Developer.** Developer is DENIED `kms:Decrypt` on the tfstate key (`042479d0-…`) — even `terraform init` fails; SRE works. Inverse for RDS IAM: `DB_USER=focus_migrator` works via Developer, PAM-fails via SRE (SRE's `rds-db:connect` policy appears to contain a literal unsubstituted template ARN — simulate-principal-policy echoes `arn:aws:rds-db:<region>:<account-id>:dbuser:…` and returns implicitDeny).
- **Backend is now committed as `backend.tf` (since #493, 2026-09-22)**, so plain `terraform init` works with no `-backend-config`. **`terraform.tfvars` is still gitignored**: copy it into any new checkout (canonical copies: `aida-emdash-postgres-node` for POC, `aida-emdash-bastion` for Dev/UAT). Older checkouts may still hold a leftover `backend.hcl`, which is harmless.
- **Stale S3 lockfile after a killed plan** (`use_lockfile = true`): `PreconditionFailed` + Lock Info on the next plan. Recovery: `pgrep -af terraform` (must be empty) → `terraform force-unlock -force <lock-id>`. Deletes only the lock, never state.
- **`rds.force_ssl` `apply_method` perpetual diff — ACCEPTED as known noise (Laith, 2026-09-18; fix PR #492 CLOSED unmerged).** Every 30-node-app plan shows `1 to change` replacing this parameter block; it is harmless and applying it is a no-op. Read POC plans as clean when this is the ONLY change. Background: RDS reports `pending-reboot` for this dynamic parameter and never updates it because the value (`1`) never changes, so declaring `immediate` makes every plan replace the block; applying does NOT clear it (the 2026-08-24 "resolved" note was wrong, it came back). The one-line fix (declare `apply_method = "pending-reboot"`) sits in closed #492 if the noise ever becomes a problem. If the diff reappears, check `aws rds describe-db-parameters --db-parameter-group-name focus-poc-node-nonprod-pg --query "Parameters[?ParameterName=='rds.force_ssl'].[ApplyType,ApplyMethod]"` and match the code to it.
- **Since 2026-09-28 branch `main` is the source for node terraform** (superseded 2026-09-28: aida-emdash now merges to main, see memory `aida-emdash-main-is-base`). History: from sync merge `eae9de04` (PR #343, 2026-08-24) until then it was `poc`, run from `aida-emdash-poc/custom/infra/terraform/envs/nonprod/30-node-app/`, not the old `poc-sync-postgres-node` checkouts. Run applies from the checkout that holds the gitignored tfvars (see below), on `main`.
- **POC image + rollout (2026-10-01, PR #607 `poc-follow-dev-tag`; applied, rev `:32`).** POC's task def tracks the mutable `:dev` tag (`container_image` default in `30-node-app/variables.tf` + tfvars). Before: `:poc-node-latest`, frozen since CI stopped pushing it. Three traps, each hit live:
  1. **`modules/ecs-app` has `lifecycle { ignore_changes = [task_definition] }` on the service** (AISVC-3062, so terraform doesn't undo CI's digest-pinned revisions on Dev/UAT). A tfvars image change → apply only REGISTERS a new revision; the service stays put. Never remove it (breaks Dev/UAT CI).
  2. **Console "Force new deployment" alone kept the service on the old revision `:31`** (still `:poc-node-latest`). First switch needs an explicit revision: `aws ecs update-service ... --task-definition focus-poc-node-nonprod-focus:32 --force-new-deployment`. The terraform replace deregisters `:31` (INACTIVE) — the running service keeps using it.
  3. **ECS resolves the tag to a digest once per deployment** (software version consistency): a replacement task keeps the old digest. A moved `:dev` reaches POC only via a new deployment.

A task-definition "replace" just registers a new revision (harmless). The `module.rds.aws_kms_key.rds[0] has moved to …rds` lines are `moved` blocks (a `count` was removed); they only rename state entries and destroy nothing.

- **`moved` blocks + `-target` (2026-09-17):** a targeted plan on a stack with `moved` blocks errors `Moved resource instances excluded by targeting` unless the OLD addresses are targeted too (`-target=module.rds.aws_kms_key.rds -target=module.rds.aws_kms_alias.rds`). A targeted apply leaves outputs stale until the next full apply. Use targeted applies for a two-phase switch (new wiring first, destroy old later) so a running task is never cut off.
